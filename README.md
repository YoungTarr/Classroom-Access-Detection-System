# ระบบตรวจจับคนเข้าใช้ห้องของหลักสูตรวิศวกรรมคอมพิวเตอร์

**Classroom Access Detection System (CADS)**

ระบบตรวจจับและจดจำใบหน้าของผู้ที่เดินเข้า-ออกห้องเรียน ผ่านกล้อง IP
โดยใช้ InsightFace + FAISS ประมวลผลบนเครื่องปลายทางเอง (on-premise ไม่ส่งข้อมูลออกนอกองค์กร)

---

## สถาปัตยกรรม

```
                      เครื่องผู้ดูแล (เบราว์เซอร์)
                                 |
                                 |  http://<ip>:3000
                                 v
    +----------------------------------------------------------+
    |  frontend : nginx  (static + reverse proxy)               |
    |             /api/ , /ws/  ->  backend:8000                |
    +----------------------------------------------------------+
                                 |
                                 v
    +----------------------------------------------------------+
    |  backend  : FastAPI + InsightFace (onnxruntime) + FAISS   |
    +----------------------------------------------------------+
                                 |
                                 v
    +----------------------------------------------------------+
    |  db       : PostgreSQL 16     |  adminer : จัดการ DB       |
    +----------------------------------------------------------+
```

ทุก service รันเป็น Docker container แยกกัน ผ่าน `docker compose`

### เครื่องปลายทาง

| รายการ | ค่า |
|---|---|
| ฮาร์ดแวร์ | Raspberry Pi 5 (RAM 8GB) |
| ระบบปฏิบัติการ | Ubuntu 24.04 LTS (ARM64) |
| โหมดการใช้งาน | headless — ไม่มีจอ ดูผ่านเบราว์เซอร์จากเครื่องอื่นในวง LAN |
| กล้อง | TP-Link Tapo C200 (RTSP, Wi-Fi 2.4GHz) |

> ระหว่างพัฒนาใช้ Windows + Docker Desktop ก่อน
> ไลบรารีทุกตัวจึงถูกเลือกให้มี wheel สำหรับ **linux/arm64 (aarch64)** ด้วย
> เพื่อให้ย้ายขึ้น Pi ได้โดยไม่ต้อง build จาก source

## เทคโนโลยีที่ใช้

| ส่วน | เทคโนโลยี |
|---|---|
| Backend | Python 3.11 + FastAPI + uvicorn |

## เริ่มต้นใช้งาน

### 1. เตรียมไฟล์ `.env`

```bash
cp .env.example .env
```

Windows (PowerShell):

```powershell
Copy-Item .env.example .env
```

จากนั้นแก้ `DB_PASSWORD` ให้เป็นรหัสผ่านของคุณเอง

> ถ้าลืมสร้าง `.env` แล้วสั่ง `docker compose up` ระบบจะหยุดทันทีพร้อมข้อความ
> บอกว่าขาดตัวแปรอะไร (ตั้งใจให้ฟ้องตั้งแต่ต้น ไม่ปล่อยให้พังทีหลัง)

### 2. สั่งรัน

```bash
docker compose up -d --build
```

### 3. เปิดใช้งาน

| หน้า | ที่อยู่ | คำอธิบาย |
|---|---|---|
| หน้าเว็บหลัก | http://localhost:3000 | สถานะระบบ + รายชื่อสมาชิก |
| Adminer | http://localhost:8080 | จัดการฐานข้อมูลผ่านเว็บ |
| API | http://localhost:8000/docs | เอกสาร API อัตโนมัติของ FastAPI |

**ข้อมูลเข้า Adminer**

| ช่อง | ค่า |
|---|---|
| System | PostgreSQL |
| Server | `db` |
| Username / Password / Database | ตามที่ตั้งไว้ใน `.env` |

> เข้าหน้าเว็บด้วย `http://localhost:3000` เท่านั้น (อย่าใช้ `127.0.0.1` หรือ IP อื่น)
> เพราะตั้งแต่เฟส 2 จะต้องขอสิทธิ์ใช้เว็บแคม ซึ่งเบราว์เซอร์อนุญาตเฉพาะ
> `localhost` หรือเว็บที่เป็น HTTPS เท่านั้น

## คำสั่งที่ใช้บ่อย

ดูสถานะ container ทั้งหมด:

```bash
docker compose ps
```

ดู log ของ backend แบบต่อเนื่อง:

```bash
docker compose logs -f backend
```

รีสตาร์ทเฉพาะ backend:

```bash
docker compose restart backend
```

หยุดทั้งระบบ (ข้อมูลใน DB ยังอยู่):

```bash
docker compose down
```

ล้างทุกอย่างรวมถึงข้อมูลใน DB (ใช้เมื่อแก้ `db/schema.sql` แล้วอยากให้รันใหม่):

```bash
docker compose down -v
```

### ที่เก็บรูปใบหน้า

ฐานข้อมูลเก็บเพียง **path** ของรูป ไฟล์จริงวางไว้ที่:

```
data/faces/<รหัสนักศึกษา>/left.jpg
data/faces/<รหัสนักศึกษา>/front.jpg
data/faces/<รหัสนักศึกษา>/right.jpg
```

เก็บ 3 มุมต่อคนเพื่อให้จดจำได้แม้หันหน้าไม่ตรงกล้อง
โฟลเดอร์นี้ถูก mount เข้า container ของ backend ที่ `/data/faces` แบบอ่านอย่างเดียว

**หลังวางรูปเสร็จ** กดปุ่ม *"โหลดรูปใบหน้าใหม่"* บนหน้าเว็บ (หรือเรียก `GET /api/faces/reload`)
ระบบจะสร้างคลังเวกเตอร์ใหม่ทันทีโดยไม่ต้องรีสตาร์ท container
และรายงานกลับมาว่าได้กี่เวกเตอร์ ไฟล์ไหนมีปัญหาอะไรบ้าง

### ข้อแนะนำในการถ่ายรูปลงทะเบียน

| ควร | ไม่ควร |
|---|---|
| แสงสม่ำเสมอ หน้าชัด | ย้อนแสง / หน้ามืด |
| มีคนเดียวในรูป | มีหลายคน (ระบบจะเลือกหน้าที่ใหญ่ที่สุดแล้วเตือน) |
| หันซ้าย-ตรง-ขวา ราว 30-45° | หันข้างจนเห็นตาข้างเดียว |
| ใบหน้ากินพื้นที่รูปพอสมควร | ถ่ายไกลจนหน้าเล็กมาก |
| ถอดแว่นกันแดด / หมวก | ใส่ของบังใบหน้า |

## ข้อตกลงในการเขียนโค้ดของโปรเจกต์นี้

1. **คอมเมนต์เป็นภาษาไทยทุกไฟล์** — ระบบนี้ต้องส่งต่อให้รุ่นน้องดูแลได้
2. **ค่า config อยู่ที่เดียว** คือ `backend/app/config.py` อ่านจาก environment เท่านั้น
   ห้าม hardcode กระจัดกระจาย และทุกค่าที่เพิ่มต้องไปเพิ่มใน `.env.example` ด้วย
3. **ห้าม fallback เงียบ ๆ** — อะไรพังต้องรายงานสาเหตุให้เห็นชัดเจน
   ไม่ใช่เดาค่าแทนแล้วทำงานต่อจนไปพังที่อื่นโดยหาต้นตอไม่เจอ
4. **ชื่อ-นามสกุลต้องมาจากฐานข้อมูลเสมอ** ห้าม hardcode ในโค้ด
5. **ไลบรารีต้องมี wheel สำหรับ ARM64** ถ้าตัวไหนไม่มี ให้หยุดแล้วรายงาน อย่าเดา

## หมายเหตุสำคัญเรื่องเว็บแคม (เฟส 2)

**ต้องเปิดหน้าเว็บด้วย `http://localhost:3000` เท่านั้น**

เบราว์เซอร์อนุญาตให้ใช้กล้อง (`getUserMedia`) เฉพาะหน้าเว็บที่เป็น *secure context*
ซึ่งมีแค่ 2 กรณี คือ `http://localhost` หรือเว็บที่เป็น **HTTPS**

| เปิดด้วย | ใช้กล้องได้ไหม |
|---|---|
| `http://localhost:3000` | ✅ ได้ |
| `http://127.0.0.1:3000` | ❌ ไม่ได้ (ถือเป็นคนละอย่างกับ localhost) |
| `http://192.168.1.x:3000` | ❌ ไม่ได้ |

> ข้อจำกัดนี้มีผลเฉพาะ **เว็บแคม** เท่านั้น
> เมื่อขึ้นเฟส 6 ที่รับภาพจากกล้อง IP โดยตรง จะเปิดดูจากเครื่องไหนในวง LAN ก็ได้
> เพราะภาพถูกดึงที่ฝั่ง backend ไม่ได้ใช้กล้องของเครื่องผู้ใช้

### ถ้าเปิดกล้องไม่ได้

| ข้อความที่ขึ้น | สาเหตุและวิธีแก้ |
|---|---|
| ไม่อนุญาตให้ใช้กล้อง | กดไอคอนกล้องบนแถบที่อยู่เว็บ เลือกอนุญาต แล้วโหลดหน้าใหม่ |
| มีโปรแกรมอื่นใช้อยู่ | ปิด Zoom / Teams / Discord / OBS หรือแท็บอื่นที่เปิดกล้องค้าง (เจอบ่อยมากบน Windows) |
| ไม่พบกล้อง | ตรวจว่าเสียบกล้องแล้ว และไม่ได้ถูกปิดไว้ใน Device Manager |

## กล้อง IP (เฟส 6)

ตั้ง `FRAME_SOURCE=rtsp` ในไฟล์ `.env` เพื่อสลับจากเว็บแคมไปใช้กล้อง IP
หน้าเว็บจะเปลี่ยนโหมดให้อัตโนมัติ ไม่ต้องแก้อะไรเพิ่ม

> โหมดนี้ **ไม่ใช้กล้องของเครื่องผู้ใช้เลย** backend เป็นคนต่อกล้องเอง
> จึงเปิดดูจากเครื่องไหนในวง LAN ก็ได้ ไม่ติดข้อจำกัด `localhost`/HTTPS แบบเว็บแคม

### เพิ่มกล้อง — แก้แค่ `.env` ไม่ต้องแตะโค้ด

กล้องทุกตัวอยู่ในรายการ `CAMERA_IDS` และมีตัวแปรของตัวเองขึ้นต้นด้วย
`CAMERA_<ชื่อกล้องตัวพิมพ์ใหญ่>_` ลำดับใน `CAMERA_IDS` คือลำดับของจอบนหน้าเว็บ

```bash
CAMERA_IDS=door_in,door_out

CAMERA_DOOR_OUT_NAME=ประตูทางออก
CAMERA_DOOR_OUT_SOURCE=rtsp
CAMERA_DOOR_OUT_HOST=192.168.1.103
CAMERA_DOOR_OUT_DIRECTION=OUT
CAMERA_DOOR_OUT_ENABLED=true
```

บัญชีผู้ใช้/พอร์ต/path ที่ใช้เหมือนกันทุกตัว ตั้งครั้งเดียวที่ `CAMERA_DEFAULT_*`
กล้องตัวไหนต่างจากค่ากลาง ค่อยกำหนดทับเฉพาะตัวนั้น (เช่น `CAMERA_DOOR_OUT_USER=...`)

จากนั้น `docker compose up -d backend` แล้วรีเฟรชหน้าเว็บ จอจะเพิ่มขึ้นมาเอง

> **ลบกล้องออก** ให้เอาชื่อออกจาก `CAMERA_IDS` (ไม่ต้องลบตัวแปร `CAMERA_DOOR_OUT_*`
> ทิ้งก็ได้ เพราะระบบอ่านเฉพาะกล้องที่อยู่ในรายการ) หรือตั้ง `..._ENABLED=false`

## กล้องสองตัวพร้อมกัน (เฟส 8)

หน้าเว็บแสดงทุกกล้องพร้อมกัน เรียงสองคอลัมน์บนจอกว้าง และซ้อนกันเป็นคอลัมน์เดียว
บนจอแคบ/มือถือ แต่ละจอมีป้าย **ประตูทางเข้า (IN)** / **ประตูทางออก (OUT)**
จุดสถานะ กรอบใบหน้า ป้ายชื่อ ป้ายทิศทาง และชุดตัวเลขสถิติ **ของตัวเองแยกกันคนละชุด**

### ใช้เว็บแคมของโน้ตบุ๊กเป็นกล้องตัวที่สองชั่วคราว

ตอนนี้มีกล้อง Tapo ตัวเดียว จึงตั้งกล้องขาออกให้รับภาพจากเว็บแคมไปก่อน
ด้วยตัวแปร `CAMERA_<ชื่อ>_SOURCE`

| ค่า | ภาพมาจากไหน | ต้องตั้งอะไรเพิ่ม |
|---|---|---|
| `rtsp` (ค่าเริ่มต้น) | backend ไปดึงจากกล้อง IP เอง | `HOST` + บัญชีผู้ใช้ |
| `browser` | เบราว์เซอร์ที่เปิดหน้าเว็บส่งภาพเว็บแคมขึ้นมาให้ | ไม่ต้องตั้งอะไรเลย |

```bash
CAMERA_DOOR_OUT_NAME=ประตูทางออก
CAMERA_DOOR_OUT_SOURCE=browser
CAMERA_DOOR_OUT_DIRECTION=OUT
CAMERA_DOOR_OUT_ENABLED=true
```

เปิดหน้าเว็บ กด **เริ่มดูภาพสดทุกกล้อง** แล้วกดอนุญาตให้ใช้กล้อง
จอขาออกจะขึ้นภาพจากเว็บแคมพร้อมกรอบและชื่อเหมือนกล้อง IP ทุกประการ

> เว็บแคมต้องเปิดหน้าเว็บผ่าน `http://localhost:3000` หรือ HTTPS เท่านั้น
> (ข้อจำกัดของเบราว์เซอร์ ไม่ใช่ของระบบนี้) และต้องเปิดหน้าค้างไว้
> ถ้าปิดแท็บ จอนั้นจะขึ้นว่าหลุด ซึ่งถูกต้องตามความจริง

**พอกล้อง Tapo ตัวที่สองมาถึง** เปลี่ยนสองบรรทัดนี้แล้วรีสตาร์ท backend
ไม่ต้องแก้โค้ดแม้แต่บรรทัดเดียว:

```bash
CAMERA_DOOR_OUT_SOURCE=rtsp
CAMERA_DOOR_OUT_HOST=192.168.1.103
```

### เส้นทางของภาพในแต่ละแบบ

```
กล้อง IP (rtsp)
    กล้อง --RTSP--> RTSPFrameSource --> AI --/ws/stream--> จอบนหน้าเว็บ

เว็บแคม (browser)
    เว็บแคม --/ws/feed--> BrowserFrameSource --> AI --/ws/stream--> จอบนหน้าเว็บ
```

ภาพเว็บแคมวนขึ้นไปแล้วกลับลงมา เพื่อให้ **ภาพที่เห็นเป็นเฟรมเดียวกับที่ AI ตรวจจริง**
เสมอ และเพื่อให้หน้าเว็บใช้โค้ดแสดงผลชุดเดียวกับกล้อง IP

### สิ่งที่แชร์กัน กับสิ่งที่แยกกัน

| | แชร์ทั้งระบบ | แยกต่อกล้อง |
|---|---|---|
| โมเดลตรวจจับ (SCRFD) | ✅ ชุดเดียว | |
| โมเดลจดจำ + FAISS index | ✅ ชุดเดียว | |
| คิวตรวจจับ (DetectScheduler) | ✅ ตัวเดียว | |
| thread อ่านกล้อง + watchdog + reconnect | | ✅ ของใครของมัน |
| ตัวติดตาม (tracker) | | ✅ ของใครของมัน |
| WebSocket + ตัวเลขสถิติ + จอบนหน้าเว็บ | | ✅ ของใครของมัน |

> **ห้ามสร้างโมเดลหรือ FAISS index แยกต่อกล้องเด็ดขาด** จะกิน RAM เพิ่มหลายร้อย MB
> โดยเปล่าประโยชน์ ซึ่ง Pi 5 ไม่มีให้เสีย เพราะต้องแบ่งให้ PostgreSQL
> และการถอดรหัสวิดีโอสองสตรีมด้วย
>
> วัดจริงบนเครื่อง dev: backend ใช้ **383 MB** ตอนกล้องเดียว และ **387 MB**
> ตอนสองกล้องตรวจจับพร้อมกัน คือเพิ่มแค่ ~3 MB ไม่ใช่เท่าตัว
> ตรวจได้เองด้วย `docker stats cads-backend`

### การแบ่ง CPU ระหว่างกล้อง

`DETECT_FPS` หมายถึง **ต่อกล้องหนึ่งตัว** ส่วน `DETECT_FPS_TOTAL` คือเพดานรวมทั้งระบบ
(ตั้ง `0` = คิดให้เองเป็น `DETECT_FPS × จำนวนกล้อง`)

กล้องทุกตัวเข้าคิวผ่านประตูเดียวกัน (`core/detect_scheduler.py`) ซึ่งปล่อยให้ตรวจ
**ทีละกล้องแบบวนคิว** ไม่ใช่แย่งกันตรวจพร้อมกัน เพราะสองงานพร้อมกันไม่ได้เร็วขึ้น
เป็นสองเท่า แต่ช้าลงทั้งคู่

กล้องที่ไม่มีเฟรมใหม่ (เช่นถูกถอดปลั๊ก) จะ **ไม่มาจองคิว** อีกตัวจึงได้คิวเต็มที่
วัดจริงแล้วสองกล้องที่ทำงานพร้อมกันได้คิวเท่ากันพอดี (46 / 46 ครั้งใน 10 วินาที)

ดูสัดส่วนที่เกิดขึ้นจริงได้จาก `GET /api/health` ที่ `frame_source.detect_scheduler.served`

### ตรวจสถานะกล้องทีละตัว

`GET /api/health` รายงานกล้องทุกตัวแยกกัน (ชื่อ ทิศทาง เชื่อมต่อ/หลุด fps จำนวนครั้ง
ที่ต่อใหม่ สาเหตุที่หลุด) และหน้าเว็บก็แสดงข้อมูลชุดเดียวกันในการ์ด "สถานะการเชื่อมต่อ"

```bash
curl -s http://localhost:8000/api/health | python -m json.tool
```

### แก้ปัญหาเมื่อกล้องตัวใดตัวหนึ่งต่อไม่ติด

จอของกล้องที่มีปัญหาจะขึ้น **กรอบเทาพร้อมสาเหตุ** ส่วนจออีกตัวยังแสดงภาพและตรวจจับ
ได้ตามปกติ ให้ไล่ตามลำดับนี้

| อาการบนจอ | สาเหตุที่พบบ่อย | วิธีตรวจ |
|---|---|---|
| `เปิดสตรีมไม่ได้ที่ rtsp://***:***@...` | กล้องไม่ได้เสียบไฟ / คนละวง LAN | `ping <ip กล้อง>` จากเครื่องที่รัน Docker |
| ต่อติดแต่ `ไม่ได้เฟรมใหม่เกิน 5 วินาที` | Wi-Fi 2.4GHz แน่นเพราะสองกล้องพร้อมกัน | ใช้ `/stream2` ทั้งคู่ และลด `CAPTURE_FPS` |
| ขึ้น 401 / ต่อไม่ได้ทั้งที่ ping ได้ | ใช้บัญชี TP-Link ID แทน Camera Account | ดูหัวข้อ "บัญชีกล้อง Tapo" ด้านบน |
| `ยังไม่มีเบราว์เซอร์ส่งภาพเว็บแคมเข้ามา` | กล้องแบบ `browser` ยังไม่มีใครเปิดหน้าเว็บ | กดปุ่มเริ่มดูภาพสด แล้วอนุญาตให้ใช้กล้อง |
| จอเว็บแคมขึ้น `NotAllowedError` | เบราว์เซอร์บล็อกกล้องไว้ | เปิดผ่าน `localhost:3000` และตรวจสิทธิ์กล้องในเบราว์เซอร์ |
| จอเว็บแคมขึ้น `NotReadableError` | โปรแกรมอื่นใช้กล้องอยู่ | ปิด Zoom / Teams / OBS แล้วลองใหม่ |

ดู log ของกล้องตัวที่มีปัญหาโดยเฉพาะ (ชื่อกล้องติดอยู่ในทุกบรรทัด):

```bash
docker compose logs -f backend | grep door_out
```

> **ถอดปลั๊กกล้องแล้วเสียบกลับ ไม่ต้องรีสตาร์ทอะไรทั้งนั้น**
> thread ของกล้องตัวนั้นจะต่อใหม่เองแบบ exponential backoff (1, 2, 4, 8 … เพดาน 30 วินาที)
> ส่วนกล้องอีกตัวไม่รู้เรื่องด้วยเลยและทำงานต่อตามปกติ

### บัญชีกล้อง Tapo

ต้องใช้ **Camera Account** ไม่ใช่บัญชี TP-Link ID ที่ล็อกอินแอป

> แอป Tapo → เลือกอุปกรณ์ → ⚙️ Settings → Advanced Settings → **Camera Account**

### เรื่องที่จัดการไว้แล้วในโค้ด

| ปัญหา | วิธีจัดการ |
|---|---|
| ภาพแตกเป็นบล็อกบน Wi-Fi 2.4GHz | บังคับใช้ TCP ผ่าน `OPENCV_FFMPEG_CAPTURE_OPTIONS` **ก่อน**สร้าง `VideoCapture` |
| ภาพช้ากว่าจริงและถ่างขึ้นเรื่อย ๆ | thread อ่านทิ้งตลอดเวลา เก็บแค่เฟรมล่าสุด (`CAP_PROP_BUFFERSIZE` ใช้ไม่ได้กับ FFMPEG) |
| RTSP ค้างแบบไม่มี error | watchdog วัดจาก "เวลาตั้งแต่ได้เฟรมดีล่าสุด" ไม่ได้เช็คแค่ `read()` คืน `False` |
| กล้องถูกถอดปลั๊ก | ต่อใหม่อัตโนมัติแบบ exponential backoff (1, 2, 4, 8 … เพดาน 30 วินาที) |
| รหัสผ่านหลุดใน log | `safe_url()` ปิดบังเป็น `rtsp://***:***@ip/path` เสมอ |
| รหัสผ่านมีอักขระพิเศษ | URL-encode อัตโนมัติ (`@` → `%40`) |

## อัตรา fps สามค่า (เฟส 7)

สามขั้นนี้เดินคนละจังหวะกันโดยสิ้นเชิง ตั้งค่าได้อิสระจาก `.env`

```
RTSPFrameSource ──► DetectionWorker ──► StreamPublisher ──► ผู้ชมทุกคน
  CAPTURE_FPS          DETECT_FPS           STREAM_FPS
  (grab/retrieve)      (AI, ต่ำ)            (JPEG, สูง)
```

| ค่า | ความหมาย | ค่าตั้งต้น |
|---|---|---|
| `CAPTURE_FPS` | ดึงเฟรมจากกล้องมาใช้ (ต่อกล้อง) | 15 |
| `DETECT_FPS` | ส่งเข้า AI (ขั้นที่แพงที่สุด) **ต่อกล้อง** | 5 |
| `DETECT_FPS_TOTAL` | เพดานการตรวจจับรวมทุกกล้อง (0 = คิดให้เอง) | 0 |
| `STREAM_FPS` | ส่งภาพไปหน้าเว็บ (ต่อกล้อง) | 15 |

เดิมทุกอย่างเดินจังหวะเดียวกัน หน้าเว็บจึงได้ภาพเท่าความเร็วของ AI (~8 fps) ซึ่งกระตุก
พอแยกแล้วภาพวิ่งที่ `STREAM_FPS` ส่วนกรอบอัปเดตตาม `DETECT_FPS`
เฟรมที่ยังไม่มีผลใหม่จะถูกทำเครื่องหมาย `is_fresh=false` แล้วหน้าเว็บ interpolate กรอบต่อเอง

**ตัวขับสตรีมมีชุดเดียวต่อหนึ่งกล้อง** ไม่ว่าจะมีคนเปิดดูกี่คน
ผู้ชมแค่มาสมัครรับภาพที่ส่งออกไป จึงไม่เกิดการรัน AI ซ้ำซ้อน

### วัดจริงบนเครื่อง dev

| ตั้งไว้ | อ่านกล้อง | ตรวจจับ | ส่งภาพ |
|---|---|---|---|
| DETECT=5 STREAM=15 | 14.0 | 5.0 | 14.0 |
| DETECT=2 STREAM=15 | 14.1 | 2.0 | **14.4** |

ลด `DETECT_FPS` ลงกว่าครึ่ง แต่ภาพยังลื่นเท่าเดิม
(กล้อง Tapo C200 บน `/stream2` ส่งได้จริงสูงสุดราว 14 fps)

### เรื่องที่ต้องรู้ตอนย้ายขึ้น Raspberry Pi

| ค่า | เหตุผล |
|---|---|
| `FACE_NUM_THREADS=3` | ปล่อยเป็น `0` แล้ว onnxruntime จะใช้ทุก core วัดจริงบนเครื่อง 12 thread ใช้ไป **6.3 core** ขณะที่ตั้ง `4` ใช้แค่ **4.0 core** และเร็วเท่ากันเป๊ะ (100 ms) |
| `CAPTURE_FPS=8-10` | ลดภาระการถอดรหัส H.264 ซึ่งกินหลาย core |
| `FACE_DET_SIZE=480` | ลดขนาดภาพที่ป้อนเข้า AI |
| `--build-arg FACE_MODEL_PACK=buffalo_s` | โมเดลตรวจจับตัวเล็กลง |
| `DETECT_FPS_TOTAL=6` | เพดานรวมของสองกล้อง ถ้าปล่อย `0` จะกลายเป็น 10 ซึ่ง Pi 5 ทำไม่ไหวเมื่อต้องถอดรหัสวิดีโอสองสตรีมไปด้วย |
| `CAMERA_DEFAULT_PATH=/stream2` | **สองกล้องพร้อมกันต้องใช้ `/stream2` ทั้งคู่** กล้อง Tapo C200 เป็น Wi-Fi 2.4GHz อย่างเดียว ถ้าใช้ `/stream1` (1080p) สองตัวจะกินแบนด์วิดท์จนภาพหายเป็นช่วง ๆ |

## หมายเหตุสำคัญเรื่องการเชื่อมต่อฐานข้อมูล

ไฟล์ `.env` กำหนด `DB_HOST=localhost` ซึ่ง **ใช้ได้เฉพาะเมื่อเชื่อมต่อจากเครื่อง host**
เช่นเปิดด้วย DBeaver หรือ psql บน Windows

แต่เมื่อ backend รันอยู่ใน container ค่านี้จะผิด เพราะ `localhost` ของ backend
หมายถึง "ตัว container backend เอง" ไม่ใช่เครื่อง host

`docker-compose.yml` จึง override ค่าให้อัตโนมัติเป็น:

| ตัวแปร | ค่าในเครื่อง host | ค่าภายใน docker network |
|---|---|---|
| `DB_HOST` | `localhost` | `db` (ชื่อ service) |
| `DB_PORT` | ตามที่ map ออกมา | `5432` เสมอ |
