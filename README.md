# ระบบตรวจจับคนเข้าใช้ห้องของหลักสูตรวิศวกรรมคอมพิวเตอร์

**Classroom Access Detection System (CADS)**

ระบบตรวจจับและจดจำใบหน้าของผู้ที่เดินเข้า-ออกห้องเรียนผ่านกล้อง IP แล้วบันทึกประวัติลงฐานข้อมูลอัตโนมัติ
ประมวลผลบนเครื่องปลายทางเองทั้งหมด (on-premise ไม่ส่งข้อมูลออกนอกองค์กร)

---

## ระบบนี้ทำอะไรได้

- **ภาพสดจากกล้อง IP สองตัวพร้อมกัน** — ประตูทางเข้า (IN) และประตูทางออก (OUT) แสดงบนหน้าเว็บเป็นสองจอ
- **ตรวจจับและติดตามใบหน้า** — กรอบใบหน้าเลื่อนตามคนอย่างลื่นไหล แต่ละคนมีหมายเลข track คงที่
- **จดจำว่าเป็นใคร** — เทียบกับรูปสมาชิกในฐานข้อมูล แสดงชื่อบนกรอบ
  (เขียว = รู้จัก / แดง = Unknown / น้ำเงิน = กำลังตรวจ)
- **บันทึกประวัติเข้า-ออกอัตโนมัติ** — ใคร เข้าหรือออก เวลาไหน กล้องไหน **พร้อมรูปใบหน้า**
  ทั้งสมาชิกและคนที่ไม่รู้จัก (Unknown)
- **จัดการสมาชิก** — รายชื่อและรูปใบหน้า 3 มุมเก็บในฐานข้อมูล นำเข้าจาก Google Form ได้ทีละหลายคน
- **ทนทาน** — กล้องหลุดแล้วต่อใหม่เอง กล้องตัวหนึ่งพังไม่กระทบอีกตัว ฐานข้อมูลช้าไม่ทำให้ภาพค้าง

## สถาปัตยกรรม

```
                      เครื่องผู้ดูแล (เบราว์เซอร์)
                                 |
                                 |  http://<ip>:3000
                                 v
    +----------------------------------------------------------+
    |  frontend : nginx  (หน้าเว็บ + reverse proxy)            |
    |             /api/ , /ws/  ->  backend:8000                |
    +----------------------------------------------------------+
                                 |
                                 v
    +----------------------------------------------------------+
    |  backend  : FastAPI + InsightFace (onnxruntime) + FAISS   |
    |             + process อ่านกล้อง RTSP แยกต่อกล้อง          |
    +----------------------------------------------------------+
           ^                     |
     RTSP  |                     v
  กล้อง Tapo x2   +----------------------------------------------+
                  |  db : PostgreSQL 16   |  adminer : จัดการ DB |
                  +----------------------------------------------+
```

ทุก service รันเป็น Docker container แยกกัน ผ่าน `docker compose`

### เส้นทางของข้อมูล

```
กล้อง --RTSP--> capture_worker (process แยก) --shared memory--> CameraRunner ของกล้องนั้น
                                                                   |
                       +-------------------------------------------+------------------------+
                       | ลูปตรวจจับ (DETECT_FPS)                                            | ลูปส่งภาพ (STREAM_FPS)
                       v                                                                    v
        detect -> track -> identify -> direction                        JPEG + ผลตรวจล่าสุด --/ws/stream--> หน้าเว็บ
                       |
                       v
          AccessLogger (คิว + thread แยก) --> ตาราง access_logs --GET /api/access-logs--> ตารางประวัติบนเว็บ
```

| ส่วน | เทคโนโลยี |
|---|---|
| Backend | Python 3.11 + FastAPI + uvicorn |
| Frontend | HTML / CSS / JavaScript ธรรมดา (ไม่มี build step) เสิร์ฟด้วย nginx |

## การจดจำและการบันทึกประวัติ

### ระบบตัดสินว่าเป็นใครอย่างไร

1. ตรวจหน้าแล้วสกัดเป็นเวกเตอร์ 512 ตัวเลข เทียบกับรูปสมาชิกทุกคนในคลัง (FAISS)
2. คะแนนความคล้ายสูงสุดถึง `SIMILARITY_THRESHOLD` (0.35) = คนนั้น ไม่ถึง = ไม่รู้จัก
3. **ไม่เชื่อผลเฟรมเดียว** — เก็บผลย้อนหลัง `IDENTITY_VOTE_WINDOW` (7) ครั้งของคนเดิม (track เดิม)
   ต้องได้เสียงตรงกันอย่างน้อย `IDENTITY_MIN_VOTES` (3) ครั้งถึงจะขึ้นชื่อ ชื่อจึงไม่กะพริบสลับคน

### กติกาการบันทึกลงตาราง `access_logs`

| | บันทึกเมื่อ | กันบันทึกซ้ำ |
|---|---|---|
| **สมาชิก** | ผลโหวตตัดสินแล้วว่าเป็นใคร (~0.6 วินาทีหลังเห็นหน้า) | ครั้งเดียวต่อ track + คนเดิมทิศทางเดิมเว้น `ACCESS_LOG_COOLDOWN_SECONDS` (30 วินาที) |
| **Unknown** | ตรวจครบ 7 ครั้งแล้ว**ไม่ตรงกับสมาชิกเลยสักครั้ง** (~1.4 วินาที) — กันสมาชิกที่เพิ่งเข้าเฟรมถูกบันทึกเป็น Unknown ปลอม | ครั้งเดียวต่อ track + กล้องเดิมทิศทางเดิมเว้น `ACCESS_LOG_UNKNOWN_COOLDOWN_SECONDS` (10 วินาที) |

- ทุกรายการเก็บ **รูปใบหน้าที่ครอปจากกล้อง** (ขยายขอบ 25% ย่อด้านยาว 240px ~10–40 KB)
- ทิศทาง IN/OUT มาจาก **การตั้งค่ากล้อง** (`CAMERA_<n>_DIRECTION`) ไม่ได้ดูจากการเดินซ้าย/ขวาในภาพ
- คนที่ยืนแช่หน้ากล้องจะถูกบันทึกครั้งเดียว ตราบใดที่ track ไม่ขาด
- การเขียนฐานข้อมูลทำใน thread แยกผ่านคิว ฐานข้อมูลช้าหรือล่มไม่ทำให้ภาพค้าง (ลองซ้ำ 3 ครั้ง)
- เวลาตั้งแต่เห็นหน้าจนขึ้นในตารางบนเว็บ ประมาณ 1–6 วินาที (ส่วนใหญ่คือรอบรีเฟรช 5 วินาทีของหน้าเว็บ)

> **ข้อจำกัดที่รู้อยู่:** สมาชิกที่หันหน้าด้านข้างมาก ๆ อาจได้คะแนนไม่ถึงเกณฑ์และถูกบันทึกเป็น Unknown
> ที่ประตูจริงคนส่วนใหญ่หันหน้าเข้ากล้องจึงเกิดน้อย ช่วยได้ด้วยการติดกล้องให้เห็นหน้าตรง

## สมาชิกและรูปใบหน้า

### ที่เก็บ

รูปใบหน้าทั้งหมดเก็บ**ในฐานข้อมูล** (ตาราง `member_photos` เป็นไฟล์ JPEG) คนละ 3 มุม: `front` / `left` / `right`
backup หรือย้ายเครื่องแค่ฐานข้อมูลอย่างเดียวก็ได้ข้อมูลครบ

### วิธีที่ 1: นำเข้าจาก Google Form (หลายคนพร้อมกัน)

ฟอร์มต้องมีคำถาม รหัสนักศึกษา / ชื่อจริง / นามสกุล / อัปโหลดรูปด้านหน้า / ด้านข้างซ้าย / ด้านข้างขวา (และเก็บอีเมล)

1. เปิด Google Sheets ของคำตอบ → **Extensions → Apps Script** → วางโค้ดจาก [scripts/google_form_export.gs](scripts/google_form_export.gs)
   → เลือกฟังก์ชัน `exportFacesForCads` → **Run** (ครั้งแรกต้องกดอนุญาตสิทธิ์)
2. ใน Google Drive จะได้โฟลเดอร์ **CADS-export** → คลิกขวา → Download ได้ไฟล์ `.zip`
3. วางไฟล์ zip ไว้ที่ `data/import/` (ไม่ต้องแตก)
4. รันโหมดทดลอง ดูแผนว่าจะนำเข้าใครบ้าง มีปัญหาอะไร (ยังไม่บันทึก):

   ```powershell
   .\scripts\import-members.ps1
   ```

5. ตรวจแล้วถูกต้อง สั่งบันทึกจริง:

   ```powershell
   .\scripts\import-members.ps1 --apply
   ```

   (Linux / Pi ใช้ `./scripts/import-members.sh` แทน) เสร็จแล้วสคริปต์สั่งโหลดคลังใบหน้าใหม่ให้เอง

**สคริปต์จัดการให้อัตโนมัติ:** แปลงรูป HEIC จาก iPhone เป็น JPG · คนเดิมส่งซ้ำใช้คำตอบล่าสุด · ตัดคำนำหน้าชื่อ (นาย/นางสาว)
· ย่อรูปด้านยาว 1600px · ตรวจว่าทุกรูปเห็นหน้าชัดหนึ่งคน · รูปเดิมไม่เขียนทับ · รันซ้ำกี่รอบก็ไม่เกิดข้อมูลซ้ำ

| ตัวเลือก | ใช้เมื่อ |
|---|---|
| `--id-from-email` | รหัสที่กรอกไม่ตรงกับเลขหน้า `@` ของอีเมล (ปกติจะข้ามแถวนั้น) ให้ใช้รหัสจากอีเมลแทน |
| `--allow-rename` | รหัสนี้มีในระบบแล้วแต่ชื่อในฟอร์มต่างไป (ปกติจะข้ามทั้งคน กันกรอกรหัสคนอื่น) และตั้งใจแก้ชื่อจริง |

นำเข้าเสร็จแล้วลบไฟล์ใน `data/import/` ทิ้งได้ (รูปอยู่ในฐานข้อมูลแล้ว)

### วิธีที่ 2: วางไฟล์เอง (ทีละคน)

1. เพิ่มรายชื่อในตาราง `members` ผ่าน Adminer (`student_id`, `first_name`, `last_name`)
2. วางรูปที่ `data/faces/<รหัสนักศึกษา>/front.jpg`, `left.jpg`, `right.jpg`
3. กด **"แสดงข้อมูลเทคนิค"** → **"โหลดรูปใบหน้าใหม่"** บนหน้าเว็บ — ระบบจะย้ายรูปเข้าฐานข้อมูล (เฉพาะมุมที่ยังไม่มี) แล้วสร้างคลังใหม่

### ข้อแนะนำในการถ่ายรูปลงทะเบียน

| ควร | ไม่ควร |
|---|---|
| แสงสม่ำเสมอ หน้าชัด | ย้อนแสง / หน้ามืด |
| มีคนเดียวในรูป | มีหลายคน (หน้าที่ไม่เด่นชัดจะถูกปฏิเสธตอนนำเข้า) |
| หันซ้าย-ตรง-ขวา ราว 30-45° | หันข้างจนเห็นตาข้างเดียว |
| ใบหน้ากินพื้นที่รูปพอสมควร | ถ่ายไกลจนหน้าเล็กมาก |
| ถอดแว่นกันแดด / หมวก | ใส่ของบังใบหน้า |

## ฐานข้อมูล

| ตาราง | เก็บอะไร |
|---|---|
| `members` | สมาชิก: `student_id` (ไม่ซ้ำ), `first_name`, `last_name`, `created_at`, `updated_at` |
| `member_photos` | รูปสมาชิก: `(student_id, angle)` เป็นคีย์, `image` (BYTEA) — ลบสมาชิกแล้วรูปถูกลบตามอัตโนมัติ |
| `access_logs` | ประวัติ: `is_unknown`, รหัส/ชื่อ (snapshot ณ เวลานั้น, NULL ถ้า Unknown), `logged_at`, `direction`, กล้อง, กรอบหน้า, `confidence`, `face_jpeg` |

- `access_logs` เก็บชื่อซ้ำในแถวและ**ไม่ผูก foreign key** กับ `members` โดยตั้งใจ ประวัติจึงยังถูกต้องแม้ภายหลังแก้ชื่อหรือลบสมาชิก
- [db/schema.sql](db/schema.sql) รัน**ครั้งเดียว**ตอนสร้าง volume ใหม่ ส่วน backend จะสร้าง/อัปเกรดตารางเองทุกครั้งที่สตาร์ท
  (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`) ฐานข้อมูลที่มีข้อมูลอยู่แล้วจึงอัปเกรดได้โดยไม่ต้องลบ —
  **แก้โครงสร้างตารางต้องแก้ทั้ง `db/schema.sql` และ `backend/app/db/database.py` ให้ตรงกัน**

### การเชื่อมต่อฐานข้อมูลจากเครื่อง host กับจากใน container

`.env` ตั้ง `DB_HOST=localhost` ซึ่ง**ใช้ได้เฉพาะเมื่อต่อจากเครื่อง host** (เช่น DBeaver หรือ psql บน Windows)
ใน container ค่านี้ผิด เพราะ `localhost` ของ backend คือตัว container เอง `docker-compose.yml` จึง override ให้:

| ตัวแปร | ค่าในเครื่อง host | ค่าภายใน docker network |
|---|---|---|
| `DB_HOST` | `localhost` | `db` (ชื่อ service) |
| `DB_PORT` | ตามที่ map ออกมา | `5432` เสมอ |

> **`DB_PASSWORD` ใช้ตั้งรหัสแค่ตอนสร้าง volume ครั้งแรกเท่านั้น**
> ถ้าเปลี่ยนใน `.env` ทีหลัง ฐานข้อมูลยังใช้รหัสเดิม backend จะต่อไม่ได้ (log ขึ้น `password authentication failed`)
> ให้แก้ `.env` กลับเป็นรหัสเดิม หรือเปลี่ยนรหัสในฐานข้อมูลให้ตรงด้วย:
>
> ```bash
> docker exec cads-postgres psql -U cads -d cads -c "ALTER USER cads WITH PASSWORD 'รหัสใหม่';"
> ```

## ตั้งค่ากล้อง IP

ตั้ง `FRAME_SOURCE=rtsp` (โหมดใช้งานจริง) backend เป็นคนต่อกล้องเอง หน้าเว็บจึงเปิดดูจากเครื่องไหนในวง LAN ก็ได้

### แก้แค่ `.env` ไม่ต้องแตะโค้ด

กล้องทุกตัวใช้ชุดตัวแปรหน้าตาเดียวกัน ต่างกันแค่ตัวเลข (ลำดับใน `CAMERA_IDS` = ลำดับจอบนหน้าเว็บ ซ้ายไปขวา)

| ตัวแปร | กล้องตัวที่ 1 (ขาเข้า) | กล้องตัวที่ 2 (ขาออก) |
|---|---|---|
| `CAMERA_<n>_NAME` | `ประตูทางเข้า` | `ประตูทางออก` |
| `CAMERA_<n>_HOST` | `192.168.1.x` | *(ว่าง = ยังไม่ได้ติดตั้ง)* |
| `CAMERA_<n>_USER` | *(ว่าง = ใช้ค่ากลาง)* | *(ว่าง = ใช้ค่ากลาง)* |
| `CAMERA_<n>_PASSWORD` | *(ว่าง = ใช้ค่ากลาง)* | *(ว่าง = ใช้ค่ากลาง)* |
| `CAMERA_<n>_PORT` | *(ว่าง = 554)* | *(ว่าง = 554)* |
| `CAMERA_<n>_PATH` | `/stream2` | `/stream2` |
| `CAMERA_<n>_DIRECTION` | `IN` | `OUT` |
| `CAMERA_<n>_ENABLED` | `true` | `true` |

```bash
CAMERA_IDS=1,2

CAMERA_1_NAME=ประตูทางเข้า
CAMERA_1_HOST=192.168.1.x
CAMERA_1_PATH=/stream2
CAMERA_1_DIRECTION=IN

CAMERA_2_NAME=ประตูทางออก
CAMERA_2_HOST=
CAMERA_2_PATH=/stream2
CAMERA_2_DIRECTION=OUT
```

ช่องที่เว้นว่างใช้ค่ากลาง `CAMERA_DEFAULT_*` กล้องตัวไหนต่างจากค่ากลาง ค่อยกำหนดทับเฉพาะตัวนั้น
เลิกใช้กล้องตัวไหน ตั้ง `..._ENABLED=false` หรือเอาออกจาก `CAMERA_IDS`

> แก้ `.env` แล้วต้องสั่ง `docker compose up -d backend` (คำสั่ง `restart` ไม่อ่าน `.env` ใหม่)

### สามสถานะของกล้องแต่ละตัว

| สถานะ (`state` ใน API) | เงื่อนไข | บนหน้าเว็บ | ระบบทำอะไร |
|---|---|---|---|
| `not_installed` | `HOST` ว่าง | จุดเทา + กรอบเส้นประ **"ยังไม่ได้ติดตั้งกล้อง"** | ไม่สร้าง process ไม่ต่อ ไม่ retry ไม่ตรวจจับ |
| `connecting` | ตั้ง `HOST` แล้วแต่ยังไม่ได้ภาพ | จุดเหลือง **"กำลังเชื่อมต่อ"** หรือจุดแดง **"กล้องหลุด"** + สาเหตุ | วนต่อใหม่แบบ exponential backoff (1, 2, 4 … เพดาน 30 วินาที) |
| `connected` | ได้ภาพใหม่อยู่จริง | จุดเขียว **"รับภาพสดอยู่"** | อ่าน ตรวจจับ และส่งภาพตามปกติ |

"ยังไม่ได้ติดตั้ง" **ไม่ถูกนับเป็นกล้องหลุด** ในสรุปบนหน้าเว็บและใน `/api/health`

ตอนสตาร์ท backend ตรวจ config กล้องที่ "รันได้แต่น่าจะผิด" (เช่น สองกล้องชี้ IP เดียวกัน, สองกล้องทิศทางเดียวกัน,
ไม่ได้ใส่บัญชีกล้อง) แล้วเตือนเป็นแถบเหลืองบนหน้าเว็บ — เตือนเฉย ๆ ไม่หยุดระบบ

### เพิ่มกล้องตัวใหม่

1. ติดตั้งกล้องด้วยแอป Tapo ให้อยู่ Wi-Fi วงเดียวกับเครื่องที่รัน Docker (C200 รองรับแค่ 2.4GHz)
2. สร้าง **Camera Account** ในแอป (ดูหัวข้อ "บัญชีกล้อง Tapo") — กล้องจะยังไม่เปิดพอร์ต 554 จนกว่าจะสร้าง
3. ตั้ง DHCP reservation ที่ router ให้ IP ของกล้องไม่เปลี่ยน
4. แก้ `CAMERA_<n>_HOST` (และ `_USER` / `_PASSWORD` ถ้าต่างจากค่ากลาง) ใน `.env`
5. `docker compose up -d backend` — หน้าเว็บที่เปิดค้างไว้จะแสดงภาพเองภายใน ~15 วินาที

### ทดสอบสองกล้องด้วยกล้องตัวเดียว

กล้อง Tapo C200 หนึ่งตัวปล่อยได้ 2 สตรีมพร้อมกัน (`/stream1` 1080p กับ `/stream2` ความละเอียดต่ำ)
จึงชี้ทั้งสองจอไปที่กล้องตัวเดียวกันได้ แค่ใช้คนละ path:

```bash
CAMERA_1_HOST=192.168.1.x
CAMERA_1_PATH=/stream2
CAMERA_2_HOST=192.168.1.x
CAMERA_2_PATH=/stream1
```

> ถอดปลั๊กกล้องแล้วจะหลุด **ทั้งสองจอ** เพราะเป็นกล้องตัวเดียวกัน
> อยากทดสอบว่า "ตัวหนึ่งหลุด อีกตัวยังทำงาน" ให้ตั้ง `CAMERA_2_HOST` เป็น IP ที่ไม่มีอยู่จริง

### แก้ปัญหาเมื่อกล้องต่อไม่ติด

จอของกล้องที่มีปัญหาขึ้นกรอบเทาพร้อมสาเหตุ ส่วนจออีกตัวยังทำงานปกติ

| อาการบนจอ | สาเหตุที่พบบ่อย | วิธีตรวจ |
|---|---|---|
| `ยังไม่ได้ติดตั้งกล้อง` | ไม่ได้ตั้ง `CAMERA_<n>_HOST` — ไม่ใช่ความผิดพลาด | ทำตาม "เพิ่มกล้องตัวใหม่" |
| `เปิดสตรีมไม่ได้ที่ rtsp://***:***@...` | **IP กล้องเปลี่ยนเองเพราะ DHCP** (พบบ่อยที่สุด) | ดูหัวข้อถัดไป |
| `เปิดสตรีมไม่ได้ที่ rtsp://***:***@...` | กล้องไม่ได้เสียบไฟ / หลุด Wi-Fi / คนละวง LAN | `ping <ip กล้อง>` จากเครื่องที่รัน Docker |
| ต่อติดแต่ `ไม่ได้เฟรมใหม่เกิน 5 วินาที` | Wi-Fi 2.4GHz แน่นเพราะสองกล้องพร้อมกัน | ใช้ `/stream2` ทั้งคู่ และลด `CAPTURE_FPS` |
| ขึ้น 401 / ต่อไม่ได้ทั้งที่ ping ได้ | ใช้บัญชี TP-Link ID แทน Camera Account | ดูหัวข้อ "บัญชีกล้อง Tapo" |

ตัวเลข **"หลุด / ลองต่อ"** บนจอ: ตัวแรก = ต่อติดแล้วหลุดทีหลังกี่ครั้ง ตัวหลัง = พยายามต่อแต่ไม่สำเร็จกี่ครั้ง

ดู log ของกล้องตัวที่มีปัญหาโดยเฉพาะ:

```bash
docker compose logs -f backend | grep "กล้อง 2"
```

> **ถอดปลั๊กกล้องแล้วเสียบกลับ ไม่ต้องรีสตาร์ทอะไร** ระบบต่อใหม่เอง และกล้องอีกตัวทำงานต่อตามปกติ

### หากล้องไม่เจอ / IP กล้องเปลี่ยนเอง

router แจก IP ให้กล้องแบบ DHCP ซึ่ง**เปลี่ยนเองได้**เมื่อกล้องหรือ router รีสตาร์ท
อาการคือหน้าเว็บขึ้น "เปิดสตรีมไม่ได้" ทั้งที่กล้องทำงานปกติ

**หา IP ปัจจุบัน:** แอป Tapo → เลือกกล้อง → ⚙️ Settings → Device Info → IP Address
หรือสแกนหาเครื่องที่เปิดพอร์ต RTSP:

```bash
nmap -p 554 --open 192.168.1.0/24
```

ได้ IP ใหม่แล้วแก้ `CAMERA_<n>_HOST` แล้ว `docker compose up -d backend`

**ทางแก้ถาวร:** ตั้ง **DHCP reservation** (Address Reservation / Static Lease) ที่ router ผูก IP กับ MAC ของกล้อง
สำคัญมากตอนรันบน Pi จริง เพราะจะไม่มีใครคอยแก้ `.env` ให้

### บัญชีกล้อง Tapo

ต้องใช้ **Camera Account** ไม่ใช่บัญชี TP-Link ID ที่ล็อกอินแอป

> แอป Tapo → เลือกอุปกรณ์ → ⚙️ Settings → Advanced Settings → **Camera Account**

### เรื่องที่จัดการไว้แล้วในโค้ด

| ปัญหา | วิธีจัดการ |
|---|---|
| อ่านกล้องได้ fps ต่ำเพราะแย่ง CPU กับ AI (GIL ของ Python) | อ่านกล้องใน **process แยก** ต่อกล้อง ส่งเฟรมผ่าน shared memory (`/dev/shm`) |
| ภาพแตกเป็นบล็อกบน Wi-Fi 2.4GHz | บังคับ RTSP ผ่าน TCP |
| ภาพช้ากว่าจริงและถ่างขึ้นเรื่อย ๆ | เก็บแค่เฟรมล่าสุด ไม่มีคิว |
| RTSP ค้างแบบไม่มี error | watchdog วัดจาก "เวลาตั้งแต่ได้เฟรมดีล่าสุด" |
| กล้องถูกถอดปลั๊ก | ต่อใหม่อัตโนมัติแบบ exponential backoff |
| รหัสผ่านหลุดใน log | `safe_url()` ปิดเป็น `rtsp://***:***@ip/path` เสมอ และกรองรหัสออกจากข้อความ error |
| รหัสผ่านมีอักขระพิเศษ | URL-encode อัตโนมัติ (`@` → `%40`) |

## ความเร็วและการแบ่ง CPU

### อัตรา fps สามค่า

```
อ่านกล้อง ──► ตรวจจับ (AI) ──► ส่งภาพ ──► ผู้ชมทุกคน
CAPTURE_FPS    DETECT_FPS       STREAM_FPS
```

| ค่า | ความหมาย | ค่าตั้งต้น |
|---|---|---|
| `CAPTURE_FPS` | ดึงเฟรมจากกล้อง (ต่อกล้อง) | 15 |
| `DETECT_FPS` | ส่งเข้า AI — ขั้นที่แพงที่สุด (ต่อกล้อง) | 5 |
| `DETECT_FPS_TOTAL` | เพดานการตรวจจับรวมทุกกล้อง (0 = `DETECT_FPS × จำนวนกล้องที่ติดตั้ง`) | 0 |
| `STREAM_FPS` | ส่งภาพไปหน้าเว็บ (ต่อกล้อง) | 15 |

สามขั้นเดินคนละจังหวะ ภาพบนเว็บจึงลื่นที่ `STREAM_FPS` ทั้งที่ AI ทำได้แค่ `DETECT_FPS`
เฟรมที่ยังไม่มีผลตรวจใหม่ หน้าเว็บจะเลื่อนกรอบต่อเอง (interpolate)
AI ทำงานชุดเดียวต่อกล้อง ไม่ว่าจะมีคนเปิดดูกี่คน (และทำงานแม้ไม่มีใครเปิดดู)

### สิ่งที่แชร์กัน กับสิ่งที่แยกกัน

| | แชร์ทั้งระบบ | แยกต่อกล้อง |
|---|---|---|
| โมเดลตรวจจับ + โมเดลจดจำ + คลังใบหน้า FAISS | ✅ ชุดเดียว | |
| คิวตรวจจับ (`DetectScheduler`) | ✅ ตัวเดียว | |
| process อ่านกล้อง + watchdog + reconnect | | ✅ |
| ตัวติดตาม (tracker) | | ✅ |
| WebSocket + ตัวเลขสถิติ + จอบนหน้าเว็บ | | ✅ |

> **ห้ามสร้างโมเดลหรือ FAISS index แยกต่อกล้อง** จะกิน RAM เพิ่มหลายร้อย MB โดยเปล่าประโยชน์
> (วัดบนเครื่อง dev: backend ~470 MB ตอนกล้องเดียว ~563 MB ตอนสองกล้อง ส่วนที่เพิ่มคือตัวถอดรหัสวิดีโอ ไม่ใช่โมเดล)

กล้องทุกตัวเข้าคิวผ่านประตูเดียวกัน ตรวจ**ทีละกล้องแบบวนคิว** ไม่แย่งกันตรวจพร้อมกัน
กล้องที่ไม่มีเฟรมใหม่ (เช่น ถูกถอดปลั๊ก) จะไม่มาจองคิว อีกตัวจึงได้คิวเต็มที่

### ค่าที่ควรปรับตอนรันบน Raspberry Pi 5

| ค่า | เหตุผล |
|---|---|
| `CAMERA_DEFAULT_PATH=/stream2` | **สองกล้องต้องใช้ `/stream2` ทั้งคู่** Pi 5 ไม่มีชิปถอดรหัส H.264 ต้องใช้ CPU และ Wi-Fi 2.4GHz รับ 1080p สองตัวไม่ไหว |
| `FACE_NUM_THREADS=3` | ปล่อย `0` แล้ว onnxruntime จะกินทุก core โดยไม่เร็วขึ้น |
| `CAPTURE_FPS=8-10` | ลดภาระการถอดรหัสวิดีโอ |
| `DETECT_FPS=3`, `DETECT_FPS_TOTAL=6` | ถ้าปล่อยเพดานเป็น `0` จะได้ 10 ซึ่ง Pi 5 ทำไม่ไหว (ชื่อจะขึ้นช้าลงเป็น ~1–2 วินาที) |
| `FACE_DET_SIZE=480` | ลดขนาดภาพที่ป้อนเข้า AI |
| `--build-arg FACE_MODEL_PACK=buffalo_s` | ตัวตรวจจับรุ่นเล็ก เร็วขึ้นหลายเท่า แต่หน้าไกลกล้องตรวจเจอยากขึ้น |

> สร้างคลังใบหน้าตอนสตาร์ท (81 รูป) ใช้ ~18 วินาทีบนเครื่อง dev บน Pi น่าจะ 1–2 นาที

## คำสั่งที่ใช้บ่อย

| ทำอะไร | คำสั่ง |
|---|---|
| ดูสถานะ container | `docker compose ps` |
| ดู log ของ backend | `docker compose logs -f backend` |
| ใช้ค่าใหม่หลังแก้ `.env` | `docker compose up -d backend` |
| รีสตาร์ท backend (ค่าเดิม) | `docker compose restart backend` |
| ดูสถานะทั้งระบบ | `curl -s http://localhost:8000/api/health` |
| ดูการใช้ RAM/CPU | `docker stats cads-backend` |
| หยุดทั้งระบบ (ข้อมูลยังอยู่) | `docker compose down` |
| **ล้างทุกอย่างรวมข้อมูลใน DB** | `docker compose down -v` |

> `restart` ใช้ container ตัวเดิมซึ่งจำค่า environment เก่าไว้ แก้ `.env` แล้วต้องใช้ `up -d` เท่านั้น
>
> `down -v` ลบ volume ของฐานข้อมูล — **สมาชิก รูป และประวัติทั้งหมดหาย** ใช้เมื่อตั้งใจเริ่มใหม่เท่านั้น

รายละเอียดและลองเรียกได้ที่ http://localhost:8000/docs

## โหมดเว็บแคม (สำหรับพัฒนา/ทดสอบ)

ตั้ง `FRAME_SOURCE=browser` เพื่อใช้เว็บแคมของเครื่องแทนกล้อง IP (ไว้ทดสอบตอนไม่มีกล้อง)

**ต้องเปิดหน้าเว็บด้วย `http://localhost:3000` เท่านั้น** เพราะเบราว์เซอร์อนุญาตให้ใช้กล้อง (`getUserMedia`)
เฉพาะ `http://localhost` หรือเว็บที่เป็น HTTPS (`127.0.0.1` หรือ `192.168.x.x` ใช้ไม่ได้)
ข้อจำกัดนี้ไม่มีผลกับโหมดกล้อง IP

| ข้อความที่ขึ้น | สาเหตุและวิธีแก้ |
|---|---|
| ไม่อนุญาตให้ใช้กล้อง | กดไอคอนกล้องบนแถบที่อยู่เว็บ เลือกอนุญาต แล้วโหลดหน้าใหม่ |
| มีโปรแกรมอื่นใช้อยู่ | ปิด Zoom / Teams / Discord / OBS หรือแท็บอื่นที่เปิดกล้องค้าง |
| ไม่พบกล้อง | ตรวจว่าเสียบกล้องแล้ว และไม่ได้ถูกปิดไว้ใน Device Manager |

## ข้อตกลงในการเขียนโค้ดของโปรเจกต์นี้

1. **คอมเมนต์เป็นภาษาไทยทุกไฟล์** — ระบบนี้ต้องส่งต่อให้รุ่นน้องดูแลได้
2. **ค่า config อยู่ที่เดียว** คือ `backend/app/config.py` อ่านจาก environment เท่านั้น
   ห้าม hardcode กระจัดกระจาย และทุกค่าที่เพิ่มต้องไปเพิ่มใน `.env.example` ด้วย
3. **ห้าม fallback เงียบ ๆ** — อะไรพังต้องรายงานสาเหตุให้เห็นชัดเจน
   ไม่ใช่เดาค่าแทนแล้วทำงานต่อจนไปพังที่อื่นโดยหาต้นตอไม่เจอ
4. **ชื่อ-นามสกุลและรูปต้องมาจากฐานข้อมูลเสมอ** ห้าม hardcode ในโค้ด
5. **ไลบรารีต้องมี wheel สำหรับ ARM64** ถ้าตัวไหนไม่มี ให้หยุดแล้วรายงาน อย่าเดา
6. **แก้โครงสร้างตารางต้องแก้สองที่** — `db/schema.sql` และ DDL ใน `backend/app/db/database.py`
7. **ข้อมูลส่วนบุคคลห้ามขึ้น git** — `.env`, `data/faces/`, `data/import/` ถูกกันไว้ใน `.gitignore`
